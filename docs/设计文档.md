锁盾（Shield）应用设计方案

目标设备 Android 9+。除激活阶段外，运行时不建议调用任何 Shizuku API。所有设计选择均为推荐性建议，实现方可依据实际场景调整。

---

一、设计目标

锁盾（Shield）的三个核心目标：

1. 保护设备免受锁机病毒、无障碍病毒、恶意设备管理器及覆盖层攻击。
2. 在非 Shell 环境下对抗 Shell 权限的禁用、停止、强杀、覆盖层等操作。即当攻击者拥有 ADB 或 Shizuku 的 Shell 身份时，锁盾仍能维持自身存活并保护其他应用。
3. 不承担清理职责——锁盾的定位是防护与阻断，严禁依赖 Shell 权限进行应用清理、卸载或数据清除。

---

二、权限模型

锁盾运行时建议持有以下三个身份：

身份 获取方式 运行时作用
设备所有者 激活阶段通过 Shizuku 执行 dpm set-device-owner 规则层：白名单、撤销授权、密码重置、应用隐藏、网络管控、调试管控、对抗 Shell
无障碍服务 激活后通过 WRITE_SECURE_SETTINGS 权限自主启用 感知层：窗口监听、点击分析、覆盖层检测、告警浮层
WRITE_SECURE_SETTINGS 激活阶段通过 Shizuku 授予 pm grant 无障碍管理权：自主启停无障碍服务、保活自身无障碍

关键原则：WRITE_SECURE_SETTINGS 是无障碍管理的核心权限，激活时通过 Shizuku 一次性授予后永久生效，此后 Shizuku 掉线或卸载均不影响该权限的使用。锁盾依靠它来保护自身无障碍服务、自主启用无障碍、以及在异常时恢复无障碍状态。

推荐的权限精简原则：

· 悬浮窗不建议申请 SYSTEM_ALERT_WINDOW，改用无障碍专属的 TYPE_ACCESSIBILITY_OVERLAY。
· 前台应用追踪不建议申请 GET_USAGE_STATS，改用无障碍事件流。
· 运行时建议不调用任何 Shizuku API。

---

三、激活阶段

3.1 辅助软件套件

软件 角色 部署方式
Shizuku 提供 Shell 权限，驱动所有 pm、dpm、am 命令 内置 APK，向导中释放安装
账户检测模块 枚举持有账户的应用 建议自行实现，不依赖外部 Accounts 应用
雹（Hail） 临时冻结持有账户或多用户的应用 内置 APK，向导中释放安装

3.2 账户检测模块的实现建议

不建议内置外部 Accounts 应用。建议参考其思路自行实现：

· 通过 Shizuku 以 Shell 身份执行 dumpsys account，解析输出中的 Account {name=..., type=...}，提取 type 字段并映射为应用包名。
· 若 dumpsys account 在部分设备上解析不稳定，可降级使用 cmd package query-services -a android.accounts.AccountAuthenticator 作为备选命令。
· 检测结果直接呈现在锁盾的 UI 中，无需用户切换到外部应用。

3.3 激活流程

阶段一：辅助软件部署

1. 释放并安装内置 Shizuku APK。
2. 引导用户启动 Shizuku：Android 11+ 通过无线调试配对；Android 9–10 通过 USB 连接执行一次启动脚本。
3. 引导用户在 Shizuku 授权管理中将锁盾加入白名单。
4. 释放并安装内置雹 APK，同样在 Shizuku 中授权。

阶段二：条件检测与自动准备

通过 Shizuku 执行 pm list users 枚举用户，通过账户检测模块获取持有账户的应用列表。UI 分为“需处理项”和“已满足项”，提供一键跳转到雹冻结界面的引导。雹支持从剪贴板导入要冻结的应用列表。

阶段三：选择设备所有者模式

建议让用户显式选择：

模式 说明 适用场景
直接成为设备所有者 锁盾自身持有设备所有者身份 用户不需要 Dhizuku 生态
通过 Dhizuku 委托 Dhizuku 成为设备所有者，锁盾请求委托 用户已使用或需要 Dhizuku 生态

若选择 Dhizuku 模式，需额外释放内置 Dhizuku APK，并通过 Shizuku 执行 dpm set-device-owner com.rosan.dhizuku/.server.DhizukuDAReceiver，然后锁盾请求 Dhizuku 委托。

阶段四：执行激活

通过 Shizuku 执行 dpm set-device-owner，目标为锁盾自身或 Dhizuku 的 receiver。激活成功后立即通过 Shizuku 执行：

· 授予 WRITE_SECURE_SETTINGS：pm grant <pkg> android.permission.WRITE_SECURE_SETTINGS。此权限永久生效，是后续无障碍管理的根基。
· 预置恢复令牌（setResetPasswordToken），引导用户导出备份。
· 设定输入法白名单（setPermittedInputMethods）。
· 记录初始设备管理器与无障碍服务快照。
· 不添加 DISALLOW_DEBUGGING_FEATURES，保持 ADB 可用。
· 不通过 Shell 写入 enabled_accessibility_services。无障碍服务的启用将在下一阶段由锁盾自身通过 WRITE_SECURE_SETTINGS 完成。

阶段五：自主启用无障碍与保活

Shizuku 使命结束后，锁盾利用已获得的 WRITE_SECURE_SETTINGS 权限：

1. 将自身无障碍服务写入 enabled_accessibility_services。
2. 通过设备所有者身份调用 setPermittedAccessibilityServices 设定初始白名单（必须包含锁盾自身）。
3. 启动无障碍管理器 fork 版的保活机制（见第五节）。

阶段六：清理与解冻

引导用户在雹中解冻临时冻结的应用。此后 Shizuku 可保留或卸载，不影响锁盾运行。

阶段七：自检

验证设备所有者（或 Dhizuku 委托）有效、无障碍服务已启用且在白名单中、WRITE_SECURE_SETTINGS 已授予、恢复令牌已预置、ADB 调试仍可用。任何一项失败均在 UI 中提示修复指引。

五、无障碍保活机制

锁盾的无障碍保活逻辑建议参考 luqijun9/AccessibilityManager fork 版的实现。该 fork 在原项目基础上新增了崩溃检测与多项保活增强。

5.1 保活组件

崩溃检测：检测无障碍服务是否“假死”——即服务在系统中显示为“已开启”但实际无法运行。检测到假死后触发重启流程。

解锁检测：设备解锁后检测无障碍服务状态。在某些设备上，解锁后无障碍服务可能被系统暂时挂起，需要主动恢复。

定时检测：以固定间隔（建议 ≥ 5 分钟）检测服务状态。过短的间隔会增加功耗，过长的间隔会延长失活窗口。

延迟 1 秒保活：在触发重启后延迟 1 秒再执行服务重启。部分设备上直接重启会失败，延迟可提高成功率。

重启强杀 app：默认重启方式为直接重启服务；如果直接重启失败，则先强制停止锁盾进程再重启。

5.2 保活与 WRITE_SECURE_SETTINGS 的协同

WRITE_SECURE_SETTINGS 使锁盾能够主动读写 enabled_accessibility_services，这是保活机制的核心能力。当检测到自身无障碍服务被从列表中移除时，锁盾直接通过该权限将自身服务重新写入列表，无需依赖 Shizuku。

这一能力是“依赖无障碍管理权限保护自身无障碍”的具体体现：锁盾不依赖设备所有者白名单来“启用”自身服务（白名单只能“允许”不能“启用”），而是通过 WRITE_SECURE_SETTINGS 直接操作 Secure Settings 来启停和保活。

5.3 与设备所有者白名单的配合

setPermittedAccessibilityServices 白名单负责规则层的阻断（非白名单服务无法启用）；WRITE_SECURE_SETTINGS 负责操作层的启停与保活。两者分工明确：白名单阻止恶意服务，WRITE_SECURE_SETTINGS 保障自身服务的存活。

六、感知层：无障碍服务

6.1 监听的事件类型

窗口状态变化（TYPE_WINDOW_STATE_CHANGED） ：记录每次前台应用切换，检测短时间内跨多个应用的连续切换，检测全屏覆盖层。

窗口内容变化（TYPE_WINDOW_CONTENT_CHANGED） ：感知安装确认、权限授予、设备管理器激活、无障碍服务启用等对话框的出现。

点击事件（TYPE_VIEW_CLICKED） ：记录点击频率、位置、目标控件。检测高频模式（如 5 秒内超过 10 次）、跨应用模式、系统设置页面反复操作。

事件来源识别：每个事件携带 event.source 和 event.packageName。若来源为锁盾自身则忽略；若来源为系统 UI，则关联到触发它的前台应用。

6.2 前台应用追踪

通过 TYPE_WINDOW_STATE_CHANGED 维护“当前前台应用”状态，记录最近 N 个前台应用的切换历史。此方式替代 GET_USAGE_STATS，不依赖额外权限。

6.3 覆盖层检测

监听窗口层级变化，当检测到非系统应用创建全屏窗口时，通过设备所有者通道查询该应用的 SYSTEM_ALERT_WINDOW 权限状态。若该应用不在信任列表中，触发告警；若窗口覆盖系统 UI，触发锁机嫌疑评估。

6.4 悬浮告警窗口

使用 TYPE_ACCESSIBILITY_OVERLAY 创建告警浮层，用于显示告警信息、恢复密码、处置结果。不建议用于日常 UI 或替代通知栏。

七、管控层：设备所有者

7.1 无障碍白名单管理

初始设定：白名单 = 系统无障碍服务 + 锁盾自身 + 用户确认的信任服务。调用 setPermittedAccessibilityServices 提交。

动态更新：每次更新前先枚举当前已启用服务，构建包含自身服务在内的完整新列表，一次性提交。若新列表遗漏当前已启用服务，设置会直接失败。建议将自身包名硬编码进白名单构建逻辑，不依赖运行时读取。

异常服务处置：感知层发现白名单内服务行为异常时，管控层将该服务移出白名单，系统立即切断其无障碍能力。

7.2 设备管理器管控

监听 ACTION_DEVICE_ADMIN_ENABLED 广播，检查激活包是否在信任列表中。若不在，调用 removeActiveAdmin 撤销。

7.3 应用管控（禁止清理）

锁盾可以对恶意应用执行以下操作：

· 隐藏并停用：setApplicationHidden(pkg, true)。
· 强制停止：forceStop。
· 撤销权限：通过设备所有者身份撤销高危权限。

锁盾严禁执行以下操作：

· pm uninstall 或等效卸载操作。
· pm clear 或等效数据清除操作。
· 任何依赖 Shell 权限的清理行为。

锁盾的定位是阻断威胁，清理决策由用户自行完成。

7.4 密码恢复

推荐默认重置为 123456 或 1234，而非随机密码。理由：覆盖层显示可能因恶意软件遮挡、无障碍服务被杀、屏幕被锁等原因失败，若密码为随机值且用户无法看到，设备将变相被锁死。简单数字密码确保用户即使看不到覆盖层也能凭记忆输入。

实现建议：

· 重置前，若当前密码策略不允许简单数字密码，可先通过 setPasswordQuality(PASSWORD_QUALITY_NUMERIC) 和 setPasswordMinimumLength(4) 临时降低要求，重置后再恢复原策略。
· 重置后，在 UI 中提示用户“已重置为临时密码，请尽快修改为强密码”。
· 安全权衡：简单密码在恢复场景下的可接受性优先于日常安全性；恢复完成后应立即引导用户修改。

7.5 网络管控（仅阻断时）

在 L3 或 L4 阻断触发时，锁盾通过设备所有者权限执行断网操作。可用的手段包括：

· 通过 UserManager.DISALLOW_CONFIG_MOBILE_NETWORKS 限制用户配置移动网络。
· 通过设备所有者 API 禁用 Wi-Fi 或修改网络配置（部分能力受厂商限制，需在目标设备上验证）。
· 作为辅助手段，可通过 setGlobalSetting 修改网络相关设置。

断网是阻断时的临时措施，处置完成后应恢复网络。

7.6 调试管控（仅阻断时）

默认保持 ADB 可用，不添加 DISALLOW_DEBUGGING_FEATURES，以支持用户对 Shizuku 及其他 ADB 工具的日常使用。

仅当 L3 或 L4 阻断触发时，临时添加 UserManager.DISALLOW_DEBUGGING_FEATURES。该限制由设备所有者设置时，将完全禁用调试功能，包括 USB 调试。

阻断处置完成后，移除该限制，恢复 ADB 使用。这是一个“熔断-恢复”机制，而非永久切断。同时在 UI 中通知用户当前状态。

7.7 ADB 放行策略

非阻断状态下，ADB 保持可用。仅当感知层检测到可疑 ADB 活动（如非白名单应用在 ADB 连接下执行高危 Shell 命令）时，才临时收紧。记录 ADB 活动时间线，供用户查看。

八、非 Shell 对抗 Shell

当攻击者拥有 Shell 权限（通过 ADB 或 Shizuku）时，锁盾的对抗手段如下。

8.1 Shell 的攻击面

Shell 命令 效果
pm disable-user <pkg> 禁用应用
pm uninstall --user 0 <pkg> 卸载应用
am force-stop <pkg> 强杀应用进程
pm revoke <pkg> <perm> 撤销权限
appops set <pkg> SYSTEM_ALERT_WINDOW allow 授予悬浮窗权限
settings put secure ... 修改 Secure Settings
dpm remove-active-admin 移除设备管理器（仅对 testOnly 应用有效）

8.2 锁盾的对抗手段

预防层（在 Shell 执行前阻止） ：

· 设备所有者应用受系统保护：Android 系统拒绝对设备所有者应用执行 pm disable-user。Shell 无法禁用锁盾。
· setUninstallBlocked ：阻止锁盾自身被卸载。Shell 的 pm uninstall 会失败。
· 无障碍白名单：阻止 Shell 通过 settings put secure enabled_accessibility_services 启用非白名单无障碍服务。即使 Shell 修改了设置，系统白名单仍会阻止非白名单服务实际运行。
· WRITE_SECURE_SETTINGS 保活：锁盾检测到自身无障碍服务被移除后，直接通过该权限重新写入，Shell 的移除操作被即时抵消。
· 按需限制（默认不启用） ：DISALLOW_APPS_CONTROL、DISALLOW_UNINSTALL_APPS、DISALLOW_CREATE_WINDOWS 仅在检测到可疑 Shell 活动时临时启用，事后恢复，以平衡防护强度与用户体验。

检测层（Shell 执行中感知） ：

· 无障碍事件流感知系统设置页面的异常操作。
· 通过设备所有者 API 定期校验 enabled_accessibility_services、设备管理器列表、应用启用状态。
· 监听 PACKAGE_CHANGED 广播，感知应用被禁用或启用。
· 监听 ADB 连接相关的系统 UI 事件（如“USB 调试已连接”通知），记录 Shell 活动时间线。

响应层（Shell 执行后恢复） ：

· 重新启用被禁用应用：检测到信任应用被 pm disable-user 禁用后，通过设备所有者身份恢复。
· 强制停止覆盖层应用：检测到非信任应用创建覆盖层后，通过设备所有者身份强制停止。
· 恢复 Secure Settings：检测到 enabled_accessibility_services 被修改且不包含锁盾自身时，通过 WRITE_SECURE_SETTINGS 直接重写。
· 撤销 Shell 授予的权限：检测到 Shell 通过 appops set 授予了非信任应用 SYSTEM_ALERT_WINDOW 后，通过设备所有者身份撤销。
· 进程存活：锁盾的进程被 am force-stop 强杀后，系统会自动重启其无障碍服务；设备所有者相关功能由系统服务托管，不依赖应用进程持续运行。

8.3 对抗能力的边界

· Shell 无法移除设备所有者（只要不声明 testOnly）。
· Shell 无法禁用设备所有者应用。
· Shell 无法卸载设备所有者应用。
· Shell 可以强杀锁盾进程，但无障碍服务会被系统重新绑定，保活层会触发重启。
· Shell 可以修改 Secure Settings，但 WRITE_SECURE_SETTINGS 保活和系统白名单会即时抵消。
· Shell 可以授予覆盖层权限，可通过按需限制或响应式强制停止对抗。

九、威胁评估引擎

9.1 事件聚合

所有感知层事件进入事件队列，按时间窗口聚合。每个事件包含事件类型、来源包名、时间戳、上下文（当前前台应用、最近应用切换历史）。

9.2 风险评分

每个事件类型有基础风险分。聚合后根据来源是否在白名单中、事件频率、事件组合、当前设备状态（锁屏状态下升权）加权。

9.3 分级决策

风险等级 触发条件 处置动作
L1 观察 单一低危事件，来源在白名单内 记录日志
L2 告警 单一高危事件，或低危事件组合 通知栏告警，悬浮窗提示
L3 切断 确认非白名单应用尝试高危操作 移出白名单 / 撤销设备管理器 / 强制停止 / 断网 / 临时禁用调试
L4 恢复 检测到锁机行为或设备已被锁定 重置密码（123456/1234）/ 隐藏恶意应用 / 断网 / 临时禁用调试 / 悬浮窗显示恢复信息

9.4 事件组合规则（推荐参考）

· 锁机嫌疑：非系统全屏覆盖层 + 前台应用反复调用锁屏 + 用户无法正常操作 → L4。
· 无障碍滥用：白名单内服务高频模拟点击 + 跨应用操作 + 系统设置页面反复点击 → L3。
· 设备管理器攻击：非白名单应用激活设备管理器 + 同时请求无障碍权限 → L3。
· 权限诱导：安装对话框出现 + 紧随其后出现权限授予对话框 + 来源应用不在信任列表 → L2。
· Shell 攻击：ADB 连接期间出现 pm disable-user / am force-stop / settings put 针对锁盾或信任应用 → L3 临时启用按需限制 + 断网 + 临时禁用调试 + 恢复被禁用应用。

十、自动阻断触发条件

设备管理器相关：

· 非白名单应用激活设备管理器 → L3 撤销。
· 白名单内应用在无用户操作情况下激活设备管理器 → L2 告警。
· 设备管理器激活后立即请求无障碍权限 → L3 撤销 + 告警。

无障碍相关：

· 非白名单应用尝试启用无障碍服务 → 系统自动拒绝，L1 记录。
· 白名单内服务高频模拟点击（5 秒内超过 10 次） → L2 告警。
· 白名单内服务跨应用连续操作（30 秒内切换超过 5 个应用） → L3 切断。
· 白名单内服务在系统设置页面反复点击授予类按钮 → L3 切断。
· 无障碍服务列表被非授权修改且不包含锁盾自身 → L3 通过 WRITE_SECURE_SETTINGS 恢复。

悬浮窗相关：

· 非信任应用创建全屏覆盖层 → L2 告警。
· 全屏覆盖层 + 锁屏调用 → L4 恢复。
· 覆盖层遮挡系统 UI → L3 强制停止。

包安装相关：

· 新安装应用声明 BIND_DEVICE_ADMIN + BIND_ACCESSIBILITY_SERVICE → L2 告警。
· 新安装应用在安装后 60 秒内请求无障碍权限 → L3 阻止启用。
· 新安装应用请求 SYSTEM_ALERT_WINDOW + 无障碍权限组合 → L2 告警。

锁机相关：

· 非系统应用调用 lockNow() → L4 恢复。
· 锁屏密码被非用户操作修改 → L4 恢复。
· 设备进入锁屏状态后，非系统应用持续持有前台焦点 → L3 强制停止。

Shell 对抗相关：

· 信任应用被 pm disable-user 禁用 → L3 重新启用 + 断网 + 临时禁用调试。
· 信任应用被 am force-stop 强杀 → L3 记录 + 断网 + 临时禁用调试。
· 非信任应用被 Shell 授予 SYSTEM_ALERT_WINDOW → L3 撤销。
· Shell 修改 enabled_accessibility_services → L3 通过 WRITE_SECURE_SETTINGS 恢复。
· Shell 尝试 dpm remove-active-admin 针对锁盾 → 系统自动拒绝，L2 记录。

十一、手动阻断

11.1 触发方式

· 通知栏常驻通知：常驻“锁盾防护中”通知，包含“紧急阻断”按钮。
· 无障碍悬浮球：通过 TYPE_ACCESSIBILITY_OVERLAY 创建可拖拽悬浮球。单击打开手动阻断面板，长按触发紧急阻断。
· 应用内手动阻断面板：打开锁盾应用，首页即为手动阻断面板，显示当前前台应用、最近事件、信任状态。
· 硬件按键组合：监听音量键组合（如音量上 + 音量下同时长按 3 秒），触发紧急阻断，无需解锁设备。
· 锁屏状态下的恢复入口：若设备已被锁机，通过悬浮告警窗口显示恢复密码（123456/1234）。用户输入解锁后，锁盾自动执行清理流程。

11.2 手动阻断动作

动作 说明 权限来源
阻断当前应用 强制停止当前前台应用，并加入黑名单 设备所有者
撤销当前应用权限 撤销设备管理器、无障碍、悬浮窗 设备所有者
隐藏当前应用 setApplicationHidden 设备所有者
重置锁屏密码 重置为 123456/1234 并显示 设备所有者
恢复无障碍白名单 重置为初始快照 + 自身服务 设备所有者 + WRITE_SECURE_SETTINGS
紧急锁定 禁止所有非白名单应用启动 设备所有者
断网 临时阻断网络连接 设备所有者
临时禁用调试 添加 DISALLOW_DEBUGGING_FEATURES 设备所有者
软处置（可选） 跳转到雹进行冻结观察 雹（需 Shizuku）

确认机制：常规手动阻断需二次确认；紧急手动阻断（悬浮球长按或硬件按键组合）无需确认；锁屏恢复通过恢复令牌验证身份后执行。

十二、UI 模块

首页（仪表盘） ：顶部显示防护状态（正常 / 告警 / 已阻断），中部显示最近 5 条事件，底部为快捷操作（手动阻断、白名单管理、恢复令牌导出）。

告警中心：按时间倒序列出所有 L2 及以上事件，每条包含时间、来源应用、事件类型、处置结果。支持按等级、应用、时间筛选，支持查看详情、撤销处置、加入白名单。

白名单管理：分设备管理器、无障碍、输入法三类。每类显示当前已启用项、已信任项、已阻断项，支持手动添加、移除、查看应用详情。

手动阻断面板：显示当前前台应用信息及其权限状态（设备管理器、无障碍、悬浮窗），提供一键阻断按钮和“为什么阻断”的解释。

恢复中心：显示恢复令牌状态，提供导出恢复令牌、恢复演练（模拟锁机场景验证恢复流程）、恢复操作记录查看。

Shell 对抗面板：显示 ADB 连接状态、最近的 Shell 活动时间线、当前是否启用了临时限制（断网 / 调试禁用）。

十三、状态机

```
[未激活] → 激活向导 → [激活中] → 自检 → [防护中]
                                          ↓
                          ┌───────────────┼───────────────┐
                          ↓               ↓               ↓
                     [告警状态]      [阻断状态]      [恢复状态]
                          ↓               ↓               ↓
                          └───────────────┴───────────────┘
                                          ↓
                                     [防护中]
```

状态转换由威胁评估引擎驱动。任何状态下，手动阻断都可立即触发 L3 或 L4 处置。

十四、容错与降级

Shizuku 掉线：运行时不调用 Shizuku。WRITE_SECURE_SETTINGS 永久有效，无障碍保活不受影响。设备所有者能力不受影响。

无障碍服务被系统杀死：保活层检测到后，通过 WRITE_SECURE_SETTINGS 直接重写 enabled_accessibility_services 恢复。若 WRITE_SECURE_SETTINGS 因某种原因失效，通知用户手动启用。

设备所有者被移除：由于不声明 testOnly，ADB 无法移除。若用户恢复出厂设置，设备所有者身份丢失，锁盾回到“未激活”状态。

恢复令牌丢失：UI 中明确提示用户导出备份，提供恢复演练让用户提前验证令牌可用性。

密码重置后覆盖层显示失败：默认重置为 123456/1234，确保用户即使看不到覆盖层也能凭记忆输入。

白名单配置错误：每次更新前做合法性检查。若更新失败，保留原白名单，记录错误日志。提供“恢复默认白名单”功能，默认白名单始终包含自身服务。

Dhizuku 委托模式下 Shizuku 掉线：已建立的 Binder 代理可能仍有效，但新的设备所有者请求无法转发。UI 提示用户重新连接 Shizuku 或切换为锁盾直接持有设备所有者身份。

Shell 攻击期间锁盾被强杀：系统会自动重启无障碍服务；设备所有者功能由系统服务托管，不依赖应用进程。锁盾重启后根据事件日志恢复处置状态。

阻断后网络/调试未恢复：处置完成后自动移除 DISALLOW_DEBUGGING_FEATURES 并恢复网络，同时在 UI 中提示用户当前状态。

十五、关键约束与建议

· 设备所有者激活的硬性前提是设备无 Google 账户、无次要用户。激活向导应严格检查并引导用户清理。
· 锁盾的 Manifest 中建议不声明 android:testOnly，以确保激活后 ADB 无法移除其设备所有者身份。
· 无障碍白名单更新时建议将锁盾自身包名硬编码进构建逻辑，避免自锁。
· 运行时建议不调用任何 Shizuku API。
· WRITE_SECURE_SETTINGS 是无障碍管理的核心权限，激活时通过 Shizuku 一次性授予，永久生效。
· 保活机制建议参考 luqijun9/AccessibilityManager fork 版，包含崩溃检测、解锁检测、定时检测、延迟重启、强杀重启。
· 严禁依赖 Shell 权限的清理行为（卸载、清除数据）。锁盾的定位是阻断威胁，清理决策由用户自行完成。
· 非紧急情况建议不阻断 ADB，仅在检测到可疑 ADB 活动或 L3/L4 阻断时临时添加调试限制，并允许用户手动移除。
· 阻断时执行断网 + 临时禁用调试，处置完成后恢复，并在 UI 中提示用户当前状态。
· 密码重置建议默认使用 123456 或 1234，避免覆盖层显示失败导致变相锁机。
· DISALLOW_APPS_CONTROL、DISALLOW_UNINSTALL_APPS、DISALLOW_CREATE_WINDOWS 建议按需启用，默认不启用，仅在检测到可疑 Shell 活动时临时启用，事后恢复。
